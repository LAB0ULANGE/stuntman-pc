## Avancement

### 1. Le temps réel en plein écran, après barriers=dedupe + texture_reuse

Presque rien : 22,7/22,0 → 22,8/23,1 images/s en 3x. Le fil GS repasse à
~100 % : en temps réel il attend ~11 % du temps le fil de rendu (sleep dans
ThreadedRenderer::Kick, la file d'une image), le reste est son travail.

### 2. Le VU1 : vu_fast, contrôlé contre l'interpréteur (`d9597ae`)

Nouveau mode `--vu-check FICHIER` (un fichier `--vu-snapshot`) : chaque run
trois fois sur un VU1 neuf - interprété, compilé, compilé rapide - comparé à
l'interpréteur (paires, registres, drapeaux sauf MAC/STATUS pour le rapide,
pipeline, mémoire, chaque quadword envoyé au GIF). 35 716 runs réels du jeu
(cascade conduite et deux fichiers d'avant), 36,7 M paires : 0 différence ;
les blocs rapides ont bien servi (drapeaux laissés dans 17 860 runs).
`regress --vu-fast` identique. En jeu : VIF1 ~85 % → ~65-75 %, mais pas
d'image en plus (le mur était le fil GS).

### 3. Le fil GS (`73a0fef`, `cd9bbf2`)

- CLUT CSM1 chargées par le CPU (texture_reuse) par décalages précalculés :
  fil GS 38,3 → 34,1 ms par image (test de l'hôte ajouté, vérifié qu'il tombe
  sur une erreur).
- La purge du cache par contenu (4 % du fil GS) et l'encadrement des
  primitives : ~7 % de travail en moins.
- Essayé et retiré : `ForNewer` sans `remove_if` à chaque appel (-0,8 %, dans
  le bruit) ; affinité un fil par cœur (rien).

### 4. barriers=precise (`7b9f670`) - le gros gain de la nuit

Les barrières mémoire complètes entre les étapes que le rendu utilise au lieu
de « toutes les commandes » : le pilote ne vide plus le GPU à chacune.
Banc 3x 35,3 → 28,8 ms (plafond sans aucune barrière : 28,2) ; cascade 3x
GPU 38,3 → 31,5 ms par image. Images identiques : regress 79/79, 19/19, et
65 images de title_to_stunt en 3x comparées à barriers=all, deux fois.

### 5. render_queue_frames=2

Seul : rien. Avec ce qui précède, il absorbe les à-coups du rendu : le jeu
moins en avance sur l'affichage (0,2-0,5 image au lieu de 1,3-2,1), donc pas
plus de latence à cette mesure.

### 7. En jouant pour de vrai : le désentrelacement prenait l'anneau du GPU (`abb718b`)

Une session entière en temps réel (comme on joue : sans `--virtual-time`)
donnait **17,6-18,9 images/s** dans la cascade, là où les mesures scriptées
(temps virtuel puis réel) en donnaient 25. Cherché en avançant le début du
temps réel (11300, 9800, 7000, 3500, 100 : toujours 25) : ce n'était pas le

la chute. Chaque trame tissée (`WeaveField`) est un envoi au GPU à elle -

le GPU (« a full ring » 12,7 s contre 0,9), le fil GS le rendu (sleep dans
Kick 41 %). Écartés en chemin : la copie ligne à ligne (une seule région :
pareil), la recréation des images de l'affichage (une fois), la mémoire du
GPU (2,3 Go sur 8), le plein écran (pareil en fenêtré).

32-34 → 48-50 images pour 100 VBlank (3 → 6) ; conduite à 4 : 25,0 images/s,
présentations 50/s, écart < 3 ms. `deinterlace=off` aurait aussi rendu la
vitesse mais montre une trame sur deux (moitié des lignes) : pas retenu.
